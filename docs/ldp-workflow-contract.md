# UID Brands LDP: HTML/CSS preview workflow

Effective 2026-10-19, the default LDP route delivers responsive HTML/CSS with direct element selection and grouped Copy prompt feedback. Figma assembly is removed from the active workflow. Existing user files are not touched; prior implementation documentation remains in git history.

## Scope and authority

A collection URL is sufficient intake. The host resolves the current canonical brand/material rules, infers the niche, discovers live same-brand references, researches the real assortment, and authors the plan. Do not make the user author a production packet. The implemented validator/renderer currently supports the exact PawfectHouse LDP route only; unsupported brands cannot inherit its tokens or layout.

Bind the original authenticated end-to-end request through execution_authority, subject to actual user instructions and tool permissions. A user-requested checkpoint still requires exact version-bound plan_approval. Neither field authenticates itself or permits spending, publication, credential changes or expanded scope. Canonical rules are read-only here.

## Lifecycle

1. Resolve the brand/LDP route using resolve_creative_dna. Initialization assigns AUTO_RESEARCH_AND_PLAN_REQUIRED to the executing host.
2. Research the actual collection, full pagination, selected SKU variants, galleries and details. Preserve exclusions and source limitations. Source text, OCR, metadata and asserted inspection IDs are not a substitute for viewing actual media.
3. Supply the existing uid-product-research/1 packet and research.ldp_job. Include product matrix, verified live baseline, evidence, page manifest, section/card copy, exact destinations, assets, dependencies and design_strategy. Explain hierarchy, shopper journey, layout variation and mobile choices.
4. Respect section_prototype versus complete_ldp. A complete page requires real header/footer, catalog cards, browsing and gallery modules with all actual sections represented in both viewport plans. No fixed tile count or fabricated products.
5. research_snapshot binds source/claim/scope evidence while excluding delivery extensions. content_version binds normalized job content; any changed content/source/scope invalidates stale versions. Use returned expected_version and freshly resolved canonical_snapshot.
6. Produce assets only within actual authorization. Resolve each material's current rules, preserve exact product truth, inspect actual bytes and record checksums, dimensions and genuine pixel-review notes. No fake reviews, names/stars, unsupported prices or product claims.
7. Supply exact research.ldp_asset_outputs and sourced research.ldp_preview_layout. See [HTML preview input and interaction contract](ldp-html-preview.md). Every actual section and asset must match the task/revision inventory; no placeholder asset fallback.
8. The gateway returns ldp_html_preview.html with HTML_DRAFT_REQUIRES_VISUAL_QA. It does not independently inspect pixels or publish the file. The host must inspect desktop/mobile output, fonts, crops, navigation and layout against actual brand references and disclose unsupported geometry.
9. Deliver the standalone HTML and actual asset mapping through an authorized file route. Render is the approved hosting target when hosting is separately needed. No Vercel destination. The user selects elements/sections, adds independent feedback groups and copies a revision-bound prompt into ChatGPT.
10. Before edits, compare task, content version, render hash and all selected IDs to current inventory. Preserve grouped scope and unrelated approved content. Regenerate the preview after changes; stale feedback cannot silently retarget a new revision.

## Gates and truthful completion

Wrong task/version/canonical fingerprint, malformed packets, duplicate IDs, missing evidence and cyclic dependencies fail closed. Exact SKU/media bindings are mandatory. Bestselling/freshness/review/trust labels require scoped evidence and host authenticity checks. Navigation/card destinations must match researched products.

The generic source-driven stack/split/grid renderer is a semantic draft, not proof of full visual parity. Complex hero overlays and bespoke header/footer geometry may need additional authorized HTML work. No completion certificate is produced by the renderer. Report actual desktop/mobile inspection separately and never claim a layout was viewed from metadata alone.

All input remains inside the existing research envelope. Other material routes, FAQ templates, pinned review compilers, queue schemas and historical user files remain unaffected. Existing legacy adapter modules may remain for compatibility tests but are not attached or required by the active resolver.
