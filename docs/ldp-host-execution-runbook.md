# LDP host execution: from verified plan to a real new Figma file

This is the operational continuation of the read-only contract. The host executes existing supported tools; it must not report the contract or its semantic operations as an executed landing page. No new credentials, service accounts, public uploads or automated publisher are needed or authorized by this runbook.

## 1. Establish the concrete pilot

Use the live Book Lovers page as the UI baseline, not its Figma demo. The product pool must be independently verified: inspect exact current collection/PDP destinations, selected SKU variants, full galleries/specs and actual product pixels. Keep the small pilot varied enough for meaningful browsing. A suggested bounded first asset batch is one desktop/mobile hero pair, two product-type images, one two-product niche combo and one UGC-style image; adapt the approved page plan to the real pool. This small batch does not permit fabricated categories or replacing actual product cards with generic imagery.

The final complete page needs native header/footer, hero, verified merchandise cards, a meaningful browsing module and a gallery, plus any other modules in its approved page manifest. Bestselling/New Arrivals only receive those labels with evidence; otherwise use truthful editorial labels. Unsupported trust offers and reviews must be omitted or replaced by verified source copy, not guessed.

## 2. Produce and bind the production plan

Resolve current LDP and relevant material rules. Use the returned LDP schema and canonical fingerprint. Submit selected-product research; record the returned research fingerprint. Author native section/card copy, destinations and asset briefs, then submit `research.ldp_job`. Resolve validation errors; bind `expected_version`. Verify the actual user's approval of this task/version and scope before generation. Stop for material commercial spending not covered by the user, required data-sharing approval or an unresolved source ambiguity. Ordinary tool availability is not authorization to spend external credits.

Act as a UI/UX designer: explain the central idea, hierarchy, shopper journey, deliberate layout variation and mobile choices in the plan. For Book Lovers, a personal reading retreat can move from an asymmetric lifestyle hero to a concise product comparison, circular browsing, a wider editorial moment and a candid gallery. Choose this rhythm for the story rather than mechanically filling rows. Preserve the current user's instruction that live web is the UI authority. Record Figma reference measurements only as demonstration context. Read a rendered mobile page before claiming mobile layout fidelity; responsive image markup alone is not a mobile QA pass.

## 3. Generate actual material assets through the host

For each independent asset, use the available image-generation tool after loading its skill. Supply the exact verified product references, current material rules and the asset's concept, dimensions, crop/copy-safe region and physical-truth requirements. Preserve source/product artwork; one generated scene is not evidence for a second product's geometry. Desktop/mobile hero must retain the same story and SKU with deliberate portrait adaptation.

Use product-source media for actual commerce cards when appropriate. Label those as source media, never as generated output. Generated UGC remains commercial image-only creative; do not add fake review names/stars/quotes.

Open each actual output and inspect pixels. Verify dimensions from actual file bytes; if the generator cannot supply required dimensions, report that boundary or use a supported authorized image-edit/export route. Do not claim a requested dimension is the delivered dimension. Save outputs through supported host/Library handling and record durable identities/checksums; no guessed download URLs. If a tool returns only an inline display image without transferable bytes, report the exact blocked asset and continue independent work.

## 4. Create a new Figma file using real supported tools

Read the current Figma create-file and use/generate-design skills before invoking tools. Create a new Design file for this pilot. Do not overwrite a supplied reference file or publish a plugin. Record the actual returned file ID/URL.

Use the Figma tool's current supported native operations to create desktop and mobile pages/frames with reusable components and Auto Layout. Build the actual header, search/navigation, hero image/copy, product cards, browsing tiles, gallery and footer. Use live-web typography/spacing/crops and responsive behavior; the generic semantic plan is a checklist, not a final geometric renderer. Product names/PDP URLs must match the verified pool; omit prices if fresh exact prices are unavailable.

Import the actual generated/source files using the supported Figma asset-upload route into known node IDs. Use IMAGE fills on native RECTANGLE/FRAME nodes; Figma does not have an IMAGE node type. Native TEXT remains text, separate from image fills. Bind shared styles/variables and preserve component instances where supported. Keep intrinsic source image dimensions separate from rendered slot and crop dimensions.

If asset upload requires a public URL but only a private Library artifact exists, use the current supported transfer route; do not expose private download links or create public storage as a workaround. Report any unsupported transfer precisely.

## 5. Read back, inspect and revise

Read actual native node IDs, parent hierarchy, types, text and image fills. Export/get actual desktop and mobile screenshots and inspect them visually at full-page and detail scale. Check native text editability, Auto Layout, catalog image/title/PDP matches, all approved sections, copy contamination, overflow, circle masks, tap targets, contrast and mobile hero continuity.

A screenshot is QA evidence, not the editable deliverable. A native node list alone is not visual proof. Correct failures using the actual target IDs; preserve unrelated edits and previously approved assets. A changed SKU invalidates its dependent imagery, claims, links and responsive variants. Verify the current file before retrying an uncertain write to avoid duplicate files/sections/uploads.

Submit the real readback receipt only after those checks. The gateway verifies structure and version binding; the host remains responsible for actual verification and truthful reporting. A section prototype cannot become a complete-page receipt by merely changing its label; it must satisfy the complete-page and approved-section inventory gates.

## 6. Deliver and stop at the authorized boundary

Return the actual user-accessible Figma file/desktop/mobile links, preview exports, original assets, source/claim/asset-node manifest, scope/limitations and completed QC. Obtain required final artistic/content review. Do not claim fully reviewed or approved based on tool success alone.

Repository PR, local test success, the gateway plan and Figma file creation are distinct milestones. Complete delivery requires the actual page and required checks. Website publication, deployment, canonical writes and any new persistent integrations remain separate authorization decisions.
